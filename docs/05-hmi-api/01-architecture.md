# 01 HMI Architecture

Depends on: [api.md](../00-contracts/api.md) (REST, WebSocket `skyranger.v1`), [README.md](../00-contracts/README.md) (value object, encodings), [tag-model.md](../00-contracts/tag-model.md) (quality codes, datatypes).

## 1. Shape

```
 browser tab
 ┌──────────────────────────────────────────────────────────────────────┐
 │ React UI (screens, components)                                       │
 │   │ useTag(path)   useAlarms()   useQuery(history)                    │
 │   ▼                                                                   │
 │ TagStore / AlarmStore  (plain TS, no React)  ◄─── LinkState           │
 │   ▲ apply snapshot/update, seq check                ▲                │
 │   │                                                 │                │
 │ WsClient (one per tab) ──── wss://host:8443/api/v1/ws (skyranger.v1)  │
 │ ApiClient (fetch)      ──── https://host:8443/api/v1/...              │
 └──────────────────────────────────────────────────────────────────────┘
```

- The HMI is a static bundle (HTML, JS, CSS, fonts, icons) served by `skyrangerd` from the same origin as the API. No Node.js server at runtime, no CDN, no internet. Fonts are bundled (decision 1: the gateway works offline).
- Single-page app with client-side routing. Every screen has a URL (`/s/{screen_name}?param=value`) so operators can bookmark and kiosks can be pointed at a screen.
- Only the public API is used (api.md section 1). Anything the HMI shows, a customer can get with `curl`.

## 2. Stack

| Concern | Choice | Why |
|---|---|---|
| Language | TypeScript, `strict: true` | Decided |
| UI | React 18 (function components, hooks) | Decided. React 19 is acceptable once our dependencies support it; nothing here relies on 19 features |
| Build | Vite | Boring, fast, static output, no SSR needed |
| Routing | React Router (data router not required) | Most common, well documented |
| Server data cache | TanStack Query | Caching, retries, invalidation for REST reads (definitions, history, alarm lists, screens) |
| Live data | Own `TagStore` + React `useSyncExternalStore` | Needs per-tag subscriptions and frame batching; generic stores re-render too much at thousands of tags |
| UI-local state | React `useState`/`useReducer`, plus a tiny context for session and preferences | Enough; no Redux or Zustand needed |
| Styling | CSS Modules + CSS custom properties (design tokens) | No runtime CSS-in-JS (CSP friendly, fast); logical properties for RTL |
| Accessible primitives | Radix UI primitives (dialog, menu, tabs, tooltip) | Unstyled, accessible, RTL-aware (`dir` prop). Details UNVERIFIED per primitive |
| Trends | uPlot | See [03-components.md](03-components.md) section 5 |
| Schema validation | Ajv (JSON Schema 2020-12) | Same schemas the server uses for screens |
| YAML | `yaml` (eemeli/yaml) npm package | Preserves comments, needed for round-trip in the editor |
| i18n | i18next + react-i18next, ICU message format plugin | Mature; see [07-i18n-a11y.md](07-i18n-a11y.md) |
| Code editor (designer) | Monaco Editor with `monaco-yaml` | JSON-Schema-driven completion for screen YAML. Bundle cost accepted only in the designer route (lazy-loaded) |
| Tests | Vitest (unit), Playwright (end-to-end against the simulator) | Standard for Vite projects |
| Lint/format | ESLint (typescript-eslint, jsx-a11y), Prettier | |

All versions pinned with a lockfile; `npm ci` in CI; dependency licenses checked (MIT/BSD/Apache/ISC only) so customers can redistribute the HMI.

Rules:
- `live` and `api-client` have no React dependency except `live/src/react.ts` (hooks). They can be unit-tested in Node and reused by a future mobile wrapper or by kiosk tooling.
- `screen-model` is also used by the gateway's screen validator via its JSON Schema files (the Go side validates with the same schema; the schema files are the shared artifact).
- The built `apps/hmi/dist` is copied into the `skyrangerd` image and served at `/`. Cache: hashed asset names with `Cache-Control: immutable`; `index.html` with `no-cache`.

## 4. State management

Three kinds of state, three mechanisms. Mixing them is the usual cause of slow HMIs.

| State | Example | Mechanism | Re-render scope |
|---|---|---|---|
| Live values | `flow_rate` current value | `TagStore` (external store) | only components bound to that tag |
| Server resources | tag definitions, screen documents, history, alarm history | TanStack Query | per query |
| UI state | open dialog, selected trend range | component state | component |

### 4.1 TagStore

```ts
// packages/live/src/types.ts
export type QualityName =
  | 'good' | 'good_manual'
  | 'uncertain' | 'uncertain_last_known' | 'uncertain_eng_range_exceeded' | 'uncertain_initial_value'
  | 'bad' | 'bad_not_connected' | 'bad_comm_failure' | 'bad_device_failure' | 'bad_config_error'
  | 'bad_out_of_service' | 'bad_waiting_for_initial_data' | 'bad_type_mismatch';

export type QualityClass = 'good' | 'uncertain' | 'bad';

/** Wire value object, exactly as README.md "canonical value object". */
export interface TagValue {
  tag_id: string;
  path: string;
  value: boolean | number | string | null; // int64/uint64 and datetime arrive as strings
  quality: QualityName | string;           // tolerate unknown codes (api.md section 8)
  ts: string;
  ts_source?: string;
  ts_gateway: string;
}

/** What components read. Derived once per update, not per render. */
export interface LiveTag {
  raw: TagValue | undefined;          // undefined = no data yet for this path
  qualityClass: QualityClass;         // unknown quality names map by prefix, else 'bad'
  tsMs: number;                       // parsed ts
  stale: StaleReason | null;          // HMI-side staleness (section 4.3)
}

export type StaleReason =
  | 'link_down'        // WebSocket not live: value is frozen in the browser
  | 'resyncing'        // waiting for snapshot after resync/reconnect
  | 'not_subscribed';  // bound but subscription failed (e.g. forbidden)
```

```ts
// packages/live/src/tagStore.ts (sketch)
export class TagStore {
  private byPath = new Map<string, LiveTag>();
  private listeners = new Map<string, Set<() => void>>();
  private dirty = new Set<string>();
  private frameScheduled = false;

  get(path: string): LiveTag { /* returns cached object; identity changes only on change */ }

  subscribe(path: string, cb: () => void): () => void { /* refcounted; drives WsClient demand */ }

  /** Called by WsClient. Replaces state for every path in the sub. */
  applySnapshot(subId: string, items: TagValue[]): void {}

  /** Called by WsClient. Only after seq check passed. */
  applyUpdate(subId: string, items: TagValue[]): void {
    for (const v of items) {
      const prev = this.byPath.get(v.path);
      if (prev?.raw && Date.parse(v.ts) < prev.tsMs) continue; // defensive; server already orders
      this.byPath.set(v.path, toLive(v));
      this.dirty.add(v.path);
    }
    this.scheduleFlush();
  }

  /** Notify listeners at most once per animation frame. */
  private scheduleFlush() {
    if (this.frameScheduled) return;
    this.frameScheduled = true;
    requestAnimationFrame(() => {        // falls back to setTimeout(…,100) when tab hidden
      this.frameScheduled = false;
      for (const p of this.dirty) this.listeners.get(p)?.forEach(cb => cb());
      this.dirty.clear();
    });
  }

  markLink(state: LinkStatus): void { /* sets stale on all entries, one notify pass */ }
}
```

```ts
// packages/live/src/react.ts
export function useTag(path: string | undefined): LiveTag {
  const store = useTagStore();
  return useSyncExternalStore(
    cb => (path ? store.subscribe(path, cb) : () => {}),
    () => (path ? store.get(path) : EMPTY),
  );
}
```

Properties:
- One map lookup per bound component per frame. A screen with 2,000 bound values where 200 change per second costs 200 small renders per second, not 2,000.
- Identity of `LiveTag` objects only changes when the tag changes, so `React.memo` components skip work.
- Values are never copied into React state or context.

### 4.2 Subscription demand (screen -> WebSocket)

Components register interest through `useTag`. The `SubscriptionManager` turns interest into WebSocket subscriptions:

- On screen mount, the resolved screen (02, section 6) already lists every bound path. The manager sends **one** `subscribe` with `paths: [...]` (max 5000 per api.md) and `sub_id = "screen:{screen_name}:{n}"`. Popups and faceplates get their own subscription.
- Ad-hoc `useTag` calls not covered by a screen subscription (e.g. a dialog) are coalesced over 50 ms into an extra subscription.
- On unmount, `unsubscribe` after a 2 s grace period (avoids churn when navigating back and forth).
- Budget: api.md allows 100 subscriptions per connection. The HMI uses at most: 1 alarms, 1 system (`_system/connections` prefix), 1 per open screen/popup, up to 10 ad-hoc. If the budget would be exceeded, ad-hoc subscriptions are merged by resubscribing a combined path list.
- `min_interval`: screens may set `refresh.min_interval` (02). Default `0s` (server batching at 100 ms is already the cap). Kiosk and mobile profiles default to `1s`.

### 4.3 Staleness in the browser

Server quality says what the gateway knows. The browser must also say when *it* has stopped knowing. `LiveTag.stale` is set by the HMI only:

| Condition | `stale` | Display |
|---|---|---|
| WS open, subscription has snapshot | `null` | per quality |
| WS closed or reconnecting | `link_down` | value kept, hatched/greyed, link banner (06) |
| After `resync` until snapshot | `resyncing` | value kept, subtle indicator, no banner if under 2 s |
| Subscribe returned `error` | `not_subscribed` | "--" with reason tooltip |

The HMI never upgrades a server quality; a `stale` flag only makes display worse.

### 4.4 AlarmStore

Same pattern, keyed by `alarm_id`, holding the alarm state object from messages.md section 5. One `subscribe` with `target: "alarms"` and `prefix` of the whole site (see [08-api-extensions.md](08-api-extensions.md) section 6 about subscribing to all alarms). Exposes derived counts (`unackedBySeverity`, `activeByPrefix(prefix)`) recomputed once per flush, used by the alarm banner and by symbols that show "alarm on this equipment".

## 5. WebSocket client

### 5.1 State machine

```
            start()
   idle ─────────────► connecting ──open──► authenticating ──welcome──► live
     ▲                     │  ▲                 │ error/4401              │
     │ stop()              │  │                 ▼                         │ close/err/
     │                     │  └── backoff ◄─────┴─────────────────────────┘ ping timeout
     │                     │      (jitter)
     │                     └──── 4401 ──► needs_login (stop, show login)
     │                     └──── 4429 ──► backoff (min 30s)
     │                     └──── 4400 ──► report bug, backoff
```

```ts
export type LinkStatus =
  | { state: 'idle' }
  | { state: 'connecting'; attempt: number; since: number }
  | { state: 'authenticating'; since: number }
  | { state: 'live'; since: number; sessionId: string; configRevision: number }
  | { state: 'backoff'; attempt: number; retryAt: number; lastError: string; downSince: number }
  | { state: 'needs_login'; reason: 'expired' | 'revoked' | 'invalid' };
```

### 5.2 Rules

- **Connect:** `new WebSocket(url, ['skyranger.v1'])`. Check `ws.protocol === 'skyranger.v1'` after open; otherwise close and show "incompatible gateway".
- **Hello:** first message `{"type":"hello","token":..., "client":"hmi/{version}"}` immediately on open (server allows 10 s).
- **Welcome:** record `config_revision`, `user.role`, `server_version`. If `server_version` major differs from the HMI's expected major, show a "reload required" banner (the HMI is served by the same gateway, so a mismatch usually means the gateway was upgraded under an open tab; reload fixes it).
- **Re-subscribe:** after every `welcome` (first connect or reconnect) re-send all active subscriptions with the same `sub_id`s. Mark all tags `resyncing` until their snapshot arrives.
- **Backoff:** full jitter, `delay = random(0, min(30s, 0.5s * 2^attempt))`, reset after 60 s live. Immediate retry when the browser fires `online` or the tab becomes visible after being hidden more than 30 s.
- **Liveness:** the browser answers server ping frames automatically, but JavaScript cannot see them (UNVERIFIED that no browser exposes them; assume not). So the client also sends application `ping` every 15 s and treats 2 missed `pong`s (30 s) as dead, closes, and reconnects. This detects half-open TCP on Wi-Fi tablets faster than waiting for the OS.
- **seq check:** per `sub_id`, `expectedSeq` resets to 1 on each `snapshot`. On `update` with `seq !== expectedSeq`: log a client bug event, `unsubscribe` then `subscribe` that `sub_id` (api.md: "a gap is a client bug or a reason to resubscribe"). Never apply an out-of-order update.
- **resync:** on `{"type":"resync"}` mark that subscription's tags `resyncing`, discard pending updates for it, wait for the `snapshot`, which replaces state. Paths missing from the new snapshot are removed from the store (they may have been deleted by a config change).
- **config_changed:** invalidate TanStack Query caches for tag definitions; re-run screen binding resolution (02, section 6). Path-subscriptions for paths that no longer resolve are re-issued with the new path if the `tag_ids` map recovers them.
- **Events subscription overflow:** on `resync` for an `events` sub, backfill with `GET /api/v1/events?start={last_seen_time}` and de-duplicate by CloudEvent `id`.
- **Errors:** `error` with `forbidden` for a subscription: mark its paths `not_subscribed`, do not retry until role changes.
- **Close 4401:** stop reconnecting, clear token, show login dialog *over* the current screen (do not navigate away; the operator keeps context). Values keep displaying as `link_down` behind the dialog.
- **Multiple tabs:** each tab has its own socket. api.md allows 20 per user; a kiosk with 3 screens uses 3. A `BroadcastChannel` shared-socket design is deferred (Open questions).

### 5.3 Token handling

Per api.md: token in memory and `sessionStorage`, never cookies, never in the URL. Kiosks use a long-lived session (see [06-operator-ergonomics.md](06-operator-ergonomics.md) section 7). REST calls that get `401 unauthenticated` trigger the same login dialog as WS 4401.

## 6. Performance budget

Target hardware: a 5-year-old office PC or a mid-range Android tablet, Chrome or Firefox current.

| Metric | Budget |
|---|---|
| Initial load (LAN, cold cache) | < 2 s to first live value; JS for viewer route < 400 KB gzipped (designer lazy) |
| Live tags on one screen | 2,000 bound, 500 changing/s, < 30% CPU on target PC |
| Alarm list | 5,000 active alarms, virtualized, scroll at 60 fps |
| Trend | 8 pens x 1 day raw at 1 s (~690k points) in < 1 s render; live append at 1 Hz with no GC stalls |
| End-to-end latency | device change to pixel < 500 ms on LAN (100 ms server batching + 1 frame) |

Techniques:
1. Per-tag external store notifications at frame rate (section 4.1).
2. No per-update object churn beyond one `LiveTag` per changed tag; formatting (`Intl.NumberFormat`) instances cached per (locale, unit, decimals).
3. SVG animation by changing attributes/CSS classes on a few elements, not by re-creating SVG trees. CSS transitions disabled for value-driven changes (they lie about timing) except the 1 Hz alarm flash.
4. Virtualized tables and alarm lists (TanStack Virtual).
5. Canvas for trends (uPlot), never SVG with thousands of nodes.
6. Hidden tabs (`document.visibilityState === 'hidden'`): keep the socket and store updated, but stop rendering (flush listeners only on visible). Alarm audio still plays.
7. Large screens: offscreen sections (tabs, collapsed panels) do not subscribe until shown.
8. A dev-only performance overlay shows updates/s, renders/s, store size, WS bytes/s.

Load test: the `sim` driver with 5,000 `random_walk` tags, Playwright opening a generated 2,000-binding screen, recording frame times and CPU via Chrome DevTools Protocol. Part of the nightly suite, not every commit.

## Decisions made
1. Static SPA served by `skyrangerd`, same origin, no runtime Node, bundled fonts, works with no internet.
2. npm-workspaces monorepo with `api-client`, `live`, `screen-model`, `components`, `tokens` packages and one `hmi` app.
3. Live values in a framework-free `TagStore` with per-path listeners and frame-batched notification, read via `useSyncExternalStore`; server resources via TanStack Query; no Redux.
4. One WebSocket per tab; one subscription per open screen with an explicit path list; refcounted ad-hoc subscriptions; 2 s unsubscribe grace.
5. WS client: full-jitter backoff capped at 30 s, application-level ping every 15 s, strict per-sub `seq` check with resubscribe on gap, re-login over the current screen.
6. Browser-side `stale` flag (`link_down`, `resyncing`, `not_subscribed`) layered on top of server quality, can only degrade display.
7. TypeScript types generated from `/api/v1/openapi.json` with `openapi-typescript`.

## Alternatives rejected and why
- **Redux / Redux Toolkit for live values**: a global reducer per update and selector re-evaluation for every connected component; too much work at 500 updates/s and too much boilerplate for a frontend-light author.
- **Zustand/Jotai for live values**: workable, but per-key subscriptions at thousands of keys end up re-implementing what `TagStore` does; keeping it framework-free also keeps it testable in Node.
- **React Context for live values**: every consumer re-renders on any change.
- **Next.js / SSR**: needs a Node server or adds static-export constraints; no benefit for an authenticated LAN app.
- **Angular or Vue**: React is decided.
- **SharedWorker holding one socket for all tabs**: fewer connections, but harder to debug, and Safari support has been inconsistent (UNVERIFIED current state). Revisit if 20-connections-per-user becomes a problem.
- **socket.io or similar**: our protocol is plain JSON over WebSocket with a defined subprotocol; a library protocol would make third-party clients harder.
- **Nx/Turborepo**: build orchestration not needed for five packages.

## Open questions
- Is 20 connections per user (api.md) enough for a control room with many kiosk tabs logged in as one account? Possibly kiosks should each have their own user (recommended in 06).
- `useSyncExternalStore` plus `requestAnimationFrame` batching: confirm with a profiling spike that React 18 concurrent rendering does not tear across components bound to the same tag (it should not with external stores; verify).
- Should `seq` gaps be reported to the server (e.g. a `POST /api/v1/client-logs`) for diagnosis? Not in the contract.
- Bundle size of Monaco in the designer route is large (several MB, UNVERIFIED exact); acceptable for engineers on LAN, not for mobile.
