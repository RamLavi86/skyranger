# 08 Fleet Management

Scope: running 5 to a few hundred gateways (topology T4, [01-topologies.md](01-topologies.md)) from one place. Binding principles from the README: the box runs alone, outbound only, removable with one command.

Fleet is **optional**. A box without `/etc/skyranger/fleet.yaml` behaves exactly as in the single-site documents. Removing the file and stopping one unit returns a box to standalone with nothing left to clean up on the box except the enrollment secrets.

## 1. Components

```
   edge box                                                 central (a Linux VM with Docker; ours or the customer's)
 ┌─────────────────────┐   HTTPS 443, outbound only    ┌──────────────────────────────────────────────┐
 │ skyrangerctl agent  │ ─────────────────────────────►│ fleet service (Go, same repo, role=fleet)    │
 │  - poll desired     │   mTLS (client cert from the  │   inventory + desired state + rollouts       │
 │  - report status    │   fleet CA) + signed docs     │   PostgreSQL (fleet DB, plain PG)            │
 │  - apply, gate      │                               │ release mirror (static files, signed)        │
 └──────────┬──────────┘                               │ tunnel endpoint (hardened sshd on 443)       │
            │ REST (localhost)                          └──────────────────────────────────────────────┘
        skyrangerd
```

- The **agent** is the only fleet client on the box. `skyrangerd` is unaware of fleet except through its public API (the agent uses an API key like `skyrangerctl config`, [05-config-as-code.md](05-config-as-code.md) section 3).
- The **fleet service** is a small Go service with its own PostgreSQL database. It is *not* the cloud-sync receiver (that is `skyranger-cloud` in [09-cloud-sync.md](09-cloud-sync.md)); they are deployed together on one central VM at first, but fleet works without sync and vice versa.
- Everything central holds about a site can be regenerated by the site: inventory is populated by what boxes report, desired state is intent only.

## 2. Inventory

Per gateway, the fleet DB stores (reported by the agent, never typed in by hand except labels):

| Field | Source |
|---|---|
| `project`, `site`, `gateway_id`, `display_name` | enrollment + `site.yaml` |
| `labels` (free key/values: `region`, `customer_contact`, `ring`) | set centrally |
| `hardware` (CPU, RAM, disk size, model, serial, packaging P1/P2/P3) | agent |
| `os` (Debian version, kernel, RAUC slot) | agent |
| `release` (installed version, channel, `previous`), `skyrangerctl` version | agent |
| `config_revision`, `config_git_sha`, `drift` state ([05](05-config-as-code.md) section 5) | agent |
| `health` (`ok`/`degraded`/`down`, last 5 `checks`), `last_seen` | agent heartbeat |
| `last_backup` (time, destination, last restore-test result) | agent |
| `clock` (offset, sync state) | agent |
| `disk` (data used %, projected days to full) | agent (`doctor`) |
| `enrolled_at`, `enrolled_by`, `cert_fingerprint`, `cert_expires` | fleet |

`gateway_id` is unique per deployment (contracts README). In fleet, the unique key is `(project, gateway_id)`, since two customers may both have `gw01` ([09](09-cloud-sync.md) multi-tenancy). Contracts reserve `{gateway_id}:{path}` for multi-gateway addressing without specifying it; fleet does not need it (it never addresses tags).

## 3. Enrollment

1. On central: `fleetctl enroll-token create --project acme --site pumphouse1 --ttl 72h` prints a one-time token (random 128 bits, single use, expires).
2. On the box: `skyrangerctl fleet enroll --url https://fleet.example.net --token <tok>`.
   - The agent generates a keypair **on the box** (the private key never leaves), sends a CSR plus inventory and the token over HTTPS (server certificate verified against a pinned fleet CA fingerprint printed by central and typed or QR-scanned in, or verified by the public CA if central uses one; the choice is recorded).
   - Central returns a short-lived-ish client certificate (default 1 year, auto-renewed at 2/3 of life) and the **fleet signing public key** (section 5). The agent writes `/etc/skyranger/fleet.yaml` (URL, CA fingerprint, fleet public key id; no secrets) and `/etc/skyranger/secrets/fleet/` (client key and certificate).
3. The token is consumed. A stolen token after use is worthless; a stolen box credential is revoked centrally (`fleetctl revoke gw01`), after which central refuses the certificate (CRL or short-lived certs; implementation detail, UNVERIFIED which).
4. **Unenroll**: `skyrangerctl fleet unenroll` (on the box, customer-owned, needs no central contact) deletes `fleet.yaml` and the fleet secrets, stops the agent's fleet module, and prints a notice to ask central to delete the record. The exit plan ([12-exit-plan.md](12-exit-plan.md)) includes this step. The customer can also disable fleet by removing the file; there is no phone-home license check anywhere.

## 4. Agent protocol (outbound HTTPS)

Pull, not push. The agent opens every connection. No inbound port, no VPN required, works through customer proxies that allow HTTPS (HTTP CONNECT proxy support is configured in `fleet.yaml`, `proxy:`; authentication to the proxy is the customer's concern).

| Call | Interval | Purpose |
|---|---|---|
| `POST /fleet/v1/heartbeat` | 60 s (+/- 20% jitter) | status document (inventory deltas, health, metrics summary). This is the **dead man's switch** central uses to alert on silence ([10-observability.md](10-observability.md)) |
| `GET /fleet/v1/desired?gateway=gw01&etag=...` | 60 s with `If-None-Match` | desired state document (section 5) |
| `POST /fleet/v1/reports` | on event | update/rollback/apply outcomes with reasons |
| `GET /fleet/v1/artifacts/...` | on demand | release bundles, config bundles; also from a customer mirror; verified by signature |

Behavior when central is unreachable: nothing changes on the box. The agent retries with exponential backoff capped at 5 minutes, keeps the last desired state, applies nothing new, and queues reports (bounded, 1000 entries, oldest dropped, with a counter). A month-long outage of central is a non-event for the site ([01](01-topologies.md)).

The `fleet/v1` API is a **new interface family**. It is specified here at the level needed for the deployment design and should be written as an OpenAPI document next to api.md once the first fleet is real. It follows the contracts' conventions (snake_case, RFC 3339 UTC ms, Go duration strings, RFC 9457 errors, UUIDv7 ids, `v1` in the path). It is not the gateway's `/api/v1`; boxes never expose it.

## 5. Desired state (signed intent)

Central stores, per gateway or per label selector, a **desired state** document the agent fetches:

```json
{
  "desired_version": 7,
  "gateway_id": "gw01",
  "issued_at": "2026-11-07T14:03:22.123Z",
  "expires_at": "2026-12-07T14:03:22.123Z",
  "release": { "version": "0.5.1", "channel": "stable", "source": "https://fleet.example.net/artifacts/0.5.1/amd64" },
  "updates": { "mode": "windowed", "window": "Sun 02:00-04:00", "allow_breaking": false, "gate_window": "10m", "require_confirm": false },
  "config": { "repo": "git@git.example.net:acme/pumphouse1.git", "ref": "main", "commit": "9f2c1d4e...", "mode": "manual" },
  "support": { "tunnel_allowed": true },
  "sync": { "enabled": true }
}
```

- The document is **signed** by the fleet signing key (Ed25519, `minisign` format like releases, [14-release-engineering.md](14-release-engineering.md) section 8, but a **different key** with a different blast radius: it can only schedule things that are themselves signed, it cannot create software). The agent verifies the signature against the key pinned at enrollment and refuses expired documents. Transport security alone is not enough: central compromise must not equal fleet compromise, and a stale replayed document must not roll a box back (`desired_version` is monotonic; the agent never accepts a lower one).
- What the document can do: select an **already-signed release** for this box, set the update policy, select a config commit for this site, allow the support tunnel to be *requested* (not opened, see section 7), enable sync. It **cannot** contain code, shell commands, secrets, or config content. Config comes from the git remote by commit sha and is validated and diffed by the box's own `skyrangerctl config apply`.
- **Local policy always wins and is always on the box**: `site.yaml` may set `fleet.accept: [release, config]` (what central may drive) and `fleet.require_local_confirm: true`. A customer who wants fleet only for monitoring sets `accept: []`; the agent then reports and ignores desired state.
- Every fleet-initiated change is recorded locally (journal and an event in the audit trail via the same mechanism as agent events, [06](06-updates-and-rollback.md) open question) with the `desired_version` and operator identity from central, so the customer's own audit log shows what we did on their box.

## 6. Config push

Push means "central says which commit"; the **box pulls and applies**:

1. Fleet operator merges to the site repo's `main` (or picks a commit); fleet sets `config.commit`.
2. Agent: `git fetch` (outbound to the git remote; the box needs read access via a deploy key in `/etc/skyranger/secrets/git/`), check the commit is in the repo's history, run offline validation ([05](05-config-as-code.md) section 7 layer 1), `config diff`.
3. Mode per site:
   - `manual`: show "pending config" in the HMI/fleet; an engineer on site (or the integrator via the tunnel) applies.
   - `staged`: apply inside the maintenance window with a health gate (`config apply --health-gate 10m`) and auto-restore on failure.
   - `auto`: apply when changed, gated.
4. Result reported back (`diverged` drift is reported and nothing is applied, 05 section 5).

For many near-identical sites (a monorepo, `sites/<id>/`), a change that is generated across sites is a normal git commit touching many site directories, rolled out by rings (section 8) so each site still gets its own diff and gate.

## 7. Outbound-only remote access

Requirement: an engineer can reach a box's shell and web UI for support, with no inbound port on the customer firewall, only when the customer allows it, and everything visible and recorded.

Design: **on-demand reverse SSH tunnel to a hardened endpoint over port 443.**

```
 box (agent)  ── ssh -R (outbound, TCP 443, key auth) ──►  tunnel endpoint (sshd, per-site user, restricted)
                                                              ▲
 support engineer  ── ssh to endpoint (2FA, jump) ────────────┘  then -> localhost:<site port> -> box sshd :22 / HTTPS :8443
```

Flow:
1. Support is **not** a permanent connection. The default state is no tunnel.
2. Opening requires **two things**: central desired state `support.tunnel_allowed: true` (we may request) **and** a local act by the customer: `skyrangerctl support enable --duration 2h` on the box console/SSH, or the HMI admin "Allow remote support" button (needs an API addition, see Open questions), or a physical/local switch on the appliance (later). A site may also set `support.always_allowed: true` in `site.yaml` for unattended pump stations; that is the customer's explicit, documented choice, and the tunnel is still time-boxed per session (maximum 8 h, re-requested).
3. The agent opens `ssh -N -R <allocated_port>:localhost:22 -p 443 tunnel@central` (and, when requested, `:8443` to reach the HMI) with a **dedicated ed25519 key** generated at enrollment, `ServerAliveInterval` set, no agent forwarding, no PTY on the endpoint side (`permitopen`/`permitlisten` restrictions on the endpoint's `authorized_keys` entry: the key may only create its own reverse listener).
4. Access to the box through the tunnel is **ordinary SSH to the box's `sshd`** with the support engineer's own key (listed in `/etc/skyranger/support_authorized_keys`, written by enrollment and visible to the customer, removable). The tunnel provides reachability; the box still authenticates the person. A shared support account is forbidden.
5. The session is **recorded** on the box (`script`/`ttyrec`-style log to `/var/lib/skyranger/support/sessions/`, readable by the customer and included in the next support bundle) and flagged while active on the console login banner and, once the API supports it (Open questions), on the HMI System page ("remote support active until 16:00, user: bob"). The internal bus `status` payload is left untouched.
6. Auto-expiry: the tunnel process is killed at `--duration` end; the agent removes the support key authorization with it. Extension needs a new enable.
7. Read-only first: `skyrangerctl diag` ([13-supportability.md](13-supportability.md)) gives read-only diagnostics without a shell and is the preferred first step; a shell is for repairs.

Why port 443 and SSH rather than something else: corporate firewalls usually permit 443 outbound; SSH-over-443 to our own endpoint is boring, auditable and has no vendor. The endpoint is plain OpenSSH `sshd` on a VM we or the customer run, with `PermitListen` restrictions (OpenSSH feature, UNVERIFIED exact config syntax per version) and `GatewayPorts no` so reverse listeners bind localhost only. Deep-packet-inspection firewalls that block SSH on 443 are a known limit: the fallback is the same tunnel carried over a WebSocket or a TLS wrapper (stunnel-style) to the endpoint (UNVERIFIED, build only on demand). Customers who ban any reverse tunnel get the diagnostics bundle workflow instead ([13](13-supportability.md)).

## 8. Rollouts and version skew

### Rings
Fleet labels set a `ring`:

| Ring | Boxes | Policy |
|---|---|---|
| 0 | our own bench and cloud simulator boxes | `nightly`/`candidate` immediately |
| 1 | pilot sites that agreed to early updates | `candidate`, then `stable` after soak |
| 2 | everyone else | `stable`, windowed, a PATCH only unless approved |

A rollout moves a release through rings with **gates between rings**: at least N boxes (default 1) healthy for T (default 48 h) with zero rollbacks, no open critical alert. A rollback or `failed_needs_human` in a ring **pauses** the rollout automatically and notifies. Fleet never updates more than one site per customer at once unless overridden, so a bad update cannot take out all of a customer's stations together.

### Version skew policy
Rules, enforced by the agent and fleet service:

1. **Gateway to gateway**: no coupling. Every gateway runs standalone with whatever it has. Mixed versions across a fleet are normal.
2. **Gateway to central (sync, 09)**: central supports the **current and previous two minors** of gateways (matching the upgrade guarantee in [14](14-release-engineering.md) section 5). The sync protocol is versioned (`sync/v1`); additive within a version. A gateway older than the window continues to run and to report heartbeats (fleet protocol is the most stable surface) but sync of data may be refused with a clear reason shown in inventory, never silently dropped.
3. **Central upgrades before gateways.** The release process publishes a central release first; gateways must never be newer than the central they sync to by more than zero minors. Central can serve a gateway one minor *ahead* only through the compatibility window; the default rule is "central >= gateway".
4. **Fleet service API** (`fleet/v1`) is stable additive within `v1`; the agent tolerates unknown fields (contracts README rule).
5. **Release selection** (`release.version`) obeys `min_from` ([14](14-release-engineering.md)); the agent computes intermediate steps itself and the fleet shows the planned chain.
6. **Config repos** carry `min_gateway_version`; fleet will not schedule a config commit for a box older than that.

## 9. Fleet operations surface

- `fleetctl` and a read-mostly web UI on the fleet service: inventory list with filters on label, version, health, silence, drift, last backup; per-site page with last 20 reports; rollout view; tunnel requests. The UI uses fleet's own API only.
- Roles on central: `viewer`, `operator` (request rollouts, request tunnels), `admin` (enroll, revoke, keys). Customer users see only their project (09 multi-tenancy).
- **Alerts** from fleet: silence (`last_seen` older than 3 heartbeats), health `down`, rollout paused, certificate expiring, backup older than policy, clock drift, disk forecast under 30 days. Delivery: email and webhook (outbound from central).
- Central stores no tag data. That is sync's job and is optional.

## 10. What if central is lost?

All inventory is rebuilt from heartbeats within minutes. Enrollment certificates are signed by the fleet CA: the CA key is backed up offline; with it, a new central takes over the same boxes (same CA, same URL or a new URL pushed through the old one before shutdown). Without the CA key, boxes must be re-enrolled with new tokens (an on-site or tunnel-assisted `skyrangerctl fleet enroll`), which is why the CA backup is a handover checklist item. Meanwhile boxes continue to operate.

## Decisions made
1. Fleet is optional and pull-based; the agent is the only fleet client; removing `fleet.yaml` and unenrolling restores a standalone box.
2. Enrollment by one-time token and an on-box generated key with a client certificate; the private key never leaves the box.
3. Desired state is a signed, expiring, monotonic document that can only select signed releases and config commits and set policy. It cannot carry code or config content.
4. Local site policy overrides fleet (`fleet.accept`, `require_local_confirm`); fleet actions are audited on the box.
5. Config push means central names a commit; the box fetches, validates, diffs, applies under a gate.
6. Remote access is an on-demand, customer-enabled, time-boxed reverse SSH tunnel to a hardened OpenSSH endpoint over 443, authenticated per person on the box, recorded locally; diagnostics come first.
7. Rollouts by rings with automatic pause; version skew rule: central >= gateway, current plus previous two minors supported, gateways never depend on each other.
8. `(project, gateway_id)` is the unique key in fleet.

## Alternatives rejected and why
- **Push model (central connects to boxes)**: needs inbound ports or a VPN to every site. Violates outbound-only.
- **Permanent VPN (WireGuard, OpenVPN, Tailscale/Headscale) to every box**: convenient, but a permanent network path into a plant OT network is exactly what OT security teams refuse; our model has no path unless the customer opens one. WireGuard remains a valid customer-owned option for sites that want it. Tailscale adds a vendor control plane; Headscale self-hosted is possible but another service to run.
- **Remote shell over MQTT or the fleet channel**: a remote-code-execution feature inside the very protocol that carries status; too easy to over-grant. Chosen design keeps command execution in SSH, per person, with a visible tunnel.
- **Cloud-managed device fleet (AWS IoT, Azure IoT Hub)**: vendor lock-in and a hard dependency on one cloud; breaks "customers can leave easily".
- **Ansible/Salt/Puppet to manage boxes**: great for the OS of boxes we own; needs inbound SSH or an agent with broad rights and a central that holds root. Fine for us as an integrator tool on top of `skyrangerctl`, not as the platform's fleet layer.
- **Kubernetes/GitOps (Flux, Argo CD) at the edge**: see README, rejected for the same reasons.
- **Unsigned desired state over TLS**: a central compromise would equal every site compromised.
- **Auto-update everything on release**: no rings, no gates; a bad release takes down every site.

## Open questions
- Contract/API: a gateway-side way for the agent to publish events into the audit trail and for the HMI to show "support active" and toggle "Allow remote support" (an admin endpoint such as `POST /api/v1/system/support`). Not in api.md; until then the toggle is console-only and the banner is a host-side file the HMI cannot read.
- Contract/API: `GET /system/info` may need `release_channel`, `packaging`, and `fleet_enrolled` fields (additive).
- Certificate revocation approach (short-lived certs vs CRL/OCSP) for fleet client certs: pick when implementing; short-lived certs avoid revocation infrastructure but need the agent to renew reliably through outages.
- `fleet/v1` OpenAPI spec and the fleet service data model are not written; this document gives only the principles and field lists.
- Hosting model for central at integrator scale: whether one fleet service serves multiple customer projects (multi-tenant) or one per customer. Interacts with [09](09-cloud-sync.md): current leaning is one fleet service for the integrator (our boxes), one sync receiver DB per project.
- SSH-over-443 on networks with deep packet inspection (see section 7) and corporate proxy authentication (NTLM proxies) are UNVERIFIED, treat as site-survey items.
- OpenSSH `PermitListen` and `restrict` options for the endpoint config: UNVERIFIED per OpenSSH version; verify on the chosen Debian release.
- Whether the HA pair (T3) enrolls as one gateway (one `gateway_id`, floating) or two members; leaning one logical gateway with a `members` list in inventory.
