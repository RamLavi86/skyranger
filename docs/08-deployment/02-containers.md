# 02 Containers: Runtime, Layout, Compose

## 1. Runtime choice: Docker Engine + Compose v2

Decision: **Docker Engine (moby, from Docker's Debian apt repository or the Debian `docker.io` package) with the Compose v2 plugin** is the only supported runtime in v1.

| Criterion | Docker Engine + Compose | Podman + Quadlet |
|---|---|---|
| Integrator familiarity (us and the next engineer) | Very high | Medium |
| Compose file as the single, readable deployment description | Native | `podman-compose` is a separate project; Quadlet uses its own unit format |
| Daemonless, rootless by default | No (rootful daemon) | Yes |
| systemd integration | Via a wrapper unit (`docker compose up`) | Native (Quadlet generates units) |
| Health-check driven restart | `restart:` policies, health status visible, no auto-restart on unhealthy alone | Quadlet / `--health-on-failure=restart` (UNVERIFIED version requirements) |
| Yocto support | `meta-virtualization` has docker-moby and podman recipes (UNVERIFIED current state per release) | same |
| Customer IT acceptance on their own Linux | Usually already approved | Common on RHEL family |

Reasoning: the product is trust and supportability. The compose file is the document a customer engineer reads to understand what runs on the box, and Docker Compose is what most of them know. Podman's rootless model is attractive for security, but we gain most of that with non-root users inside containers, read-only root filesystems, dropped capabilities and no published DB ports. The security doc may revisit this.

Portability guardrails so we can switch later:
- Only Compose Specification features that `podman compose` also handles (no Swarm `deploy:` blocks except `resources.limits`, no Docker-only log drivers other than `journald`).
- Images are plain OCI, built with `docker buildx`, pushed with digests.
- Our supervision lives in systemd and `skyrangerctl`, not in Docker's restart policies alone.

## 2. Images

| Image | Base | Contents | User |
|---|---|---|---|
| `ghcr.io/<org>/skyrangerd` | `gcr.io/distroless/static-debian12` or `debian:13-slim` (see Open questions) | `skyrangerd`, all `skyranger-driver-*` binaries, HMI static build in `/usr/share/skyranger/hmi`, DB migrations in `/usr/share/skyranger/migrations`, config migrators | `10001:10001` |
| `ghcr.io/<org>/skyranger-sim` | same | simulator (MQTT/Sparkplug, Modbus TCP, OPC UA) with fault injection (decision 7) | `10001` |
| `timescale/timescaledb:<pinned>-pg17` | upstream | PostgreSQL 17 + TimescaleDB (exact tag is pinned per release, UNVERIFIED which tag scheme we will pin to; we pin by digest regardless) | upstream `postgres` |
| `eclipse-mosquitto:2.0.<pinned>` | upstream | broker | `mosquitto` |

`<org>` is a placeholder; the registry choice is in [14-release-engineering.md](14-release-engineering.md). Every image reference in a deployed compose file is **pinned by digest** (`image: ...@sha256:...`). Tags are for humans only.

Driver packaging follows [driver-interface.md](../00-contracts/driver-interface.md) section 1: drivers are child processes inside the `skyrangerd` container, not containers. A third-party driver container is supported via the shared `/run/skyranger/drivers` socket directory (sketched below as a commented service).

## 3. Host directory layout

All state is in bind mounts at known paths. Nothing important lives in Docker-managed volumes.

```
/etc/skyranger/                       host config, root:skyranger 0750
  skyranger.env                       compose environment (gateway_id, ports, profile list, DB URL)
  site.yaml                           site identity: gateway_id, site name, customer, contact, topology
  secrets/                            file-backed secret store (0700), resolved for secret:// refs
    mqtt/gateway                      (secret://mqtt/gateway)
    db/skyranger                      database password
    tls/server.crt, server.key        HTTPS + MQTT TLS (security doc owns rotation)
  mosquitto/mosquitto.conf, acl       broker config (generated by skyrangerctl from templates)
  fleet.yaml                          optional: fleet enrollment (absent = no fleet)
  release.lock                        currently active release manifest (signed copy)

/var/lib/skyranger/                   data, root:skyranger 0750
  postgres/                           PGDATA (bind mount, owned by container postgres uid)
  mosquitto/                          broker persistence (retained messages)
  spool/historian/                    historian on-disk WAL when DB unavailable
  state/
    config-snapshot.yaml              last applied config revision (see 01-topologies T2)
    boot-health.json                  last N boot health results (update gating)
  config-git/                         local git repo mirror of config (05-config-as-code)
  backups/                            nightly backups, rotated
  releases/<version>/                 unpacked release bundles: compose.yaml, manifest, signatures
  releases/current -> <version>       symlink, switched atomically on update
  releases/previous -> <version>
  support/                            generated support bundles (auto-pruned)

/run/skyranger/                       tmpfs
  drivers/*.sock                      driver gRPC sockets (inside skyrangerd container)
  agent.sock                          skyrangerctl agent control socket

/usr/local/bin/skyrangerctl           host tool (also shipped in each release bundle)
/etc/systemd/system/skyranger*.service, *.timer
```

Disk layout recommendation (generic PC): one SSD, ext4, with `/var/lib/skyranger` on its own partition or LV so a full data disk cannot fill `/`. Mount with `noatime`. (Power-loss rationale in [11-time-and-power.md](11-time-and-power.md).)

## 4. Networks and ports

| Port | Service | Bound to | Purpose |
|---|---|---|---|
| 8443/tcp | skyrangerd | OT LAN interface | HMI, REST, WS ([api.md](../00-contracts/api.md)) |
| 8883/tcp | mosquitto | OT LAN interface | MQTT over TLS for devices and read-only subscribers |
| 1883/tcp | mosquitto | compose network only | internal plaintext for `skyrangerd`, simulator |
| 5432/tcp | postgres | compose network only (never published) | |
| 123/udp | chrony (host) | OT LAN | NTP server for devices |
| 22/tcp | sshd (host) | OT LAN / maintenance interface only | local maintenance |
| 9100/tcp | skyrangerd metrics | localhost or LAN, configurable | Prometheus metrics (see 10-observability) |

Milestone 1 note on MQTT TLS: the ESP32 firmware may start with plain 1883 on an isolated test LAN. The compose file below exposes 1883 on the host only under profile `dev`. Production never publishes 1883 (security doc confirms).

## 5. Compose file for the vertical slice

Release bundles ship this file at `/var/lib/skyranger/releases/<version>/compose.yaml`, with digests filled in by the release pipeline. Values in `${...}` come from `/etc/skyranger/skyranger.env`.

```yaml
# Sky Ranger vertical slice. Compose Specification.
# Profiles:  (none) = core: mosquitto, postgres, skyrangerd
#            sim    = adds simulator
#            dev    = adds hmi-dev (Vite), plain 1883 on host, adminer
# Project name is fixed so container names are predictable in runbooks.
name: skyranger

x-common: &common
  restart: unless-stopped
  logging:
    driver: journald
    options:
      tag: "skyranger/{{.Name}}"
  security_opt:
    - no-new-privileges:true
  cap_drop: [ALL]

networks:
  core:
    driver: bridge
    ipam:
      config:
        - subnet: 172.30.42.0/24        # fixed, avoids clashing with plant subnets; overridable

services:
  postgres:
    <<: *common
    image: timescale/timescaledb@sha256:<digest>      # PG 17 + TimescaleDB, pinned by release
    profiles: ["", "db"]                              # see note: disabled in T2 via SKYRANGER_EXTERNAL_DB
    cap_add: [CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETUID]   # postgres entrypoint needs these
    environment:
      POSTGRES_DB: skyranger
      POSTGRES_USER: skyranger
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
      PGDATA: /var/lib/postgresql/data/pgdata
    command:
      - postgres
      - -c
      - shared_preload_libraries=timescaledb
      - -c
      - synchronous_commit=on             # power-loss safety; see 11-time-and-power
      - -c
      - full_page_writes=on
      - -c
      - shared_buffers=${PG_SHARED_BUFFERS:-512MB}
      - -c
      - max_wal_size=1GB
    volumes:
      - /var/lib/skyranger/postgres:/var/lib/postgresql/data
    secrets: [db_password]
    networks: [core]
    shm_size: 256m
    stop_grace_period: 60s                 # let postgres checkpoint cleanly
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U skyranger -d skyranger"]
      interval: 10s
      timeout: 5s
      retries: 6
      start_period: 60s

  mosquitto:
    <<: *common
    image: eclipse-mosquitto@sha256:<digest>
    cap_add: [SETGID, SETUID]
    volumes:
      - /etc/skyranger/mosquitto:/mosquitto/config:ro
      - /etc/skyranger/secrets/tls:/mosquitto/certs:ro
      - /var/lib/skyranger/mosquitto:/mosquitto/data
    ports:
      - "${SKYRANGER_LAN_ADDR:-0.0.0.0}:8883:8883"
    networks: [core]
    healthcheck:
      # mosquitto_sub against $SYS on the internal listener, exits after 1 msg
      test: ["CMD-SHELL", "mosquitto_sub -h localhost -p 1883 -t '$$SYS/broker/uptime' -C 1 -W 5 -u healthcheck -P \"$$(cat /mosquitto/config/healthcheck.pw)\""]
      interval: 15s
      timeout: 8s
      retries: 4

  skyrangerd:
    <<: *common
    image: ghcr.io/<org>/skyrangerd@sha256:<digest>
    user: "10001:10001"
    read_only: true
    tmpfs:
      - /tmp:size=64m
      - /run/skyranger:size=16m,uid=10001,gid=10001   # driver sockets
    environment:
      SKYRANGER_GATEWAY_ID: ${SKYRANGER_GATEWAY_ID}
      SKYRANGER_DB_URL: ${SKYRANGER_DB_URL:-postgres://skyranger@postgres:5432/skyranger?sslmode=disable}
      SKYRANGER_DB_PASSWORD_FILE: /run/secrets/db_password
      SKYRANGER_SECRETS_DIR: /etc/skyranger/secrets
      SKYRANGER_HTTP_ADDR: ":8443"
      SKYRANGER_METRICS_ADDR: ":9100"
      SKYRANGER_STATE_DIR: /var/lib/skyranger/state
      SKYRANGER_SPOOL_DIR: /var/lib/skyranger/spool
      SKYRANGER_LOG_LEVEL: info
      SKYRANGER_LOG_FORMAT: json
      SKYRANGER_RELEASE: ${SKYRANGER_RELEASE}
    volumes:
      - /etc/skyranger/secrets:/etc/skyranger/secrets:ro
      - /var/lib/skyranger/state:/var/lib/skyranger/state
      - /var/lib/skyranger/spool:/var/lib/skyranger/spool
      # third-party driver containers would share this via a named tmpfs; see commented service
    ports:
      - "${SKYRANGER_LAN_ADDR:-0.0.0.0}:8443:8443"
      - "${SKYRANGER_METRICS_BIND:-127.0.0.1}:9100:9100"
    secrets: [db_password]
    networks: [core]
    depends_on:
      postgres:
        condition: service_healthy
        required: false          # T2: postgres not running locally (UNVERIFIED: `required` needs Compose >= 2.20)
      mosquitto:
        condition: service_healthy
    stop_grace_period: 30s       # drivers get 5 s on SIGTERM (driver-interface.md), then checkpoint derived_state
    healthcheck:
      test: ["CMD", "/usr/bin/skyrangerd", "healthcheck", "--url", "https://localhost:8443/api/v1/system/health", "--insecure-localhost"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 120s         # migrations may run at start

  simulator:
    <<: *common
    image: ghcr.io/<org>/skyranger-sim@sha256:<digest>
    profiles: ["sim"]
    user: "10001:10001"
    read_only: true
    environment:
      SIM_MQTT_URL: mqtt://mosquitto:1883
      SIM_SPARKPLUG_GROUP: skyranger
      SIM_SCENARIO: /etc/sim/scenario.yaml
      SIM_MODBUS_LISTEN: ":5020"
      SIM_OPCUA_LISTEN: ":4840"
      SIM_CONTROL_ADDR: ":8090"     # fault injection API
    volumes:
      - /etc/skyranger/sim:/etc/sim:ro
    networks: [core]

  # ---- dev profile only ----
  hmi-dev:
    image: node:22-bookworm-slim     # dev only, not digest-pinned
    profiles: ["dev"]
    working_dir: /src/hmi
    command: ["npm", "run", "dev", "--", "--host", "0.0.0.0"]
    volumes: ["${SKYRANGER_SRC:-../..}:/src"]
    ports: ["5173:5173"]
    networks: [core]

  mosquitto-plain-dev:
    image: alpine/socat@sha256:<digest>   # exposes internal 1883 on the host for the ESP32 bench
    profiles: ["dev"]
    command: ["TCP-LISTEN:1883,fork,reuseaddr", "TCP:mosquitto:1883"]
    ports: ["1883:1883"]
    networks: [core]

  # ---- example third-party driver container (not shipped) ----
  # driver-acme:
  #   image: example/skyranger-driver-acme@sha256:...
  #   command: ["--socket", "/run/skyranger/drivers/acme1.sock", "--connection", "acme1"]
  #   volumes: [driver-sockets:/run/skyranger/drivers]
  #   (skyrangerd would then mount the same volume instead of its private tmpfs)

secrets:
  db_password:
    file: /etc/skyranger/secrets/db/skyranger
```

Notes on the sketch:
- The `profiles: ["", "db"]` line on `postgres` is illustrative. Compose has no "empty profile" syntax; the real mechanism is: `skyrangerctl` generates `COMPOSE_PROFILES` from `site.yaml` (`db,sim` etc.) and the postgres service carries `profiles: ["db"]`, with `db` on by default. To be finalized when the file is first run.
- Using Docker `restart: unless-stopped` gives process-level restart. Restart on *unhealthy* is not native in Docker for non-Swarm containers (UNVERIFIED for current Docker versions), so the `skyrangerctl agent` watches health status and restarts a container that stays unhealthy for its threshold ([10-observability.md](10-observability.md)).
- `logging.driver: journald` puts every container's logs into the host journal with the container name, so one `journalctl` covers host and containers, and log rotation is journald's job.
- No container has `privileged`, host networking or the Docker socket. The `skyrangerctl agent` runs on the host and is the only thing that talks to the Docker API.

## 6. systemd units on the host

`skyranger.service` owns the compose project, so the platform starts at boot in the right order and systemd is the single supervisor that the hardware watchdog trusts.

```ini
# /etc/systemd/system/skyranger.service
[Unit]
Description=Sky Ranger gateway (compose project)
Requires=docker.service
After=docker.service network-online.target chrony.service time-sync.target
Wants=network-online.target time-sync.target
# do not start the stack before the clock is sane; see 11-time-and-power
ConditionPathExists=/etc/skyranger/skyranger.env

[Service]
Type=oneshot
RemainAfterExit=yes
EnvironmentFile=/etc/skyranger/skyranger.env
WorkingDirectory=/var/lib/skyranger/releases/current
ExecStartPre=/usr/local/bin/skyrangerctl preflight         # disk space, clock, secrets present, release signature
ExecStart=/usr/bin/docker compose --env-file /etc/skyranger/skyranger.env up -d --wait --wait-timeout 300
ExecStop=/usr/bin/docker compose --env-file /etc/skyranger/skyranger.env down --timeout 60
TimeoutStartSec=420
TimeoutStopSec=120

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/skyranger-agent.service
[Unit]
Description=Sky Ranger host agent (health supervision, updates, backups, fleet)
After=skyranger.service
Wants=skyranger.service

[Service]
Type=notify
ExecStart=/usr/local/bin/skyrangerctl agent
Restart=always
RestartSec=5s
WatchdogSec=30s                 # agent pings sd_notify WATCHDOG=1 only when its own checks pass
NotifyAccess=main
User=root                       # needs Docker API and system control; see Open questions

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/skyranger-backup.timer
[Unit]
Description=Nightly Sky Ranger backup
[Timer]
OnCalendar=*-*-* 02:17:00
RandomizedDelaySec=15m
Persistent=true
[Install]
WantedBy=timers.target
# skyranger-backup.service: ExecStart=/usr/local/bin/skyrangerctl backup create --rotate
```

`docker compose up --wait` requires a reasonably recent Compose v2 (UNVERIFIED minimum version; pin the Compose plugin version in the install script).

## Decisions made
1. Docker Engine + Compose v2 only in v1, with portability guardrails so Podman can be added later.
2. One `skyrangerd` image that also carries all first-party drivers and the built HMI; no separate HMI container in production.
3. All images pinned by digest in deployed compose files.
4. Bind mounts under `/etc/skyranger` and `/var/lib/skyranger` only; no Docker-managed volumes for state.
5. journald as the log driver for all containers.
6. A systemd unit owns the compose project; a host agent supervises health beyond what Docker restart policies do.
7. Containers run as non-root where the upstream image allows, read-only root filesystems, `cap_drop: ALL`, no published DB port.
8. Fixed compose project name `skyranger` and fixed internal subnet (overridable) so runbooks are predictable.

## Alternatives rejected and why
- **Podman + Quadlet as the default**: better security posture, but less familiar to integrators and customer engineers, and the compose file is our human-readable deployment description. Kept possible by guardrails.
- **Named Docker volumes**: hidden under `/var/lib/docker`, easy to delete with `docker volume prune`, awkward to back up and to hand to a customer.
- **Container per driver**: rejected by driver-interface.md; we follow it.
- **Watchtower-style auto-update of `:latest` tags**: unpinned, unsigned, not health-gated, no coordinated migrations.
- **Docker `json-file` logs**: a second log location with its own rotation config; journald already rotates and is where host logs are.

## Open questions
- Base image for `skyrangerd`: distroless static (smaller, no shell) vs `debian:13-slim` (a shell for field debugging). Distroless means support uses `docker cp` of a static busybox or the host tools. Leaning distroless plus a separate `skyranger-debug` image; confirm with the security doc.
- `debian:13` as the host OS assumes Debian 13 is the current stable at release time (it was released in 2025 per memory; UNVERIFIED). The fallback is Debian 12.
- The agent runs as root to drive Docker. The security doc should decide whether a narrower helper (a polkit rule or a socket-activated root helper with a fixed command set) is required.
- Metrics port 9100 collides with the Prometheus node_exporter default. Pick another port (e.g. 9452) once we check the Prometheus default port allocations list (UNVERIFIED).
- `api.md` fixes the HTTPS port at 8443 and TLS always on. The container healthcheck therefore needs a localhost TLS exception; a plain-HTTP health listener on a Unix socket might be cleaner. Proposed to the API owner.
