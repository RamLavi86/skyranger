# Messages Contract

Status: v1 contract. Depends on [tag-model.md](tag-model.md) (values, quality, `counter_total`) and [README.md](README.md) (naming, encodings).

There are three message families. They never share a topic root.

| Family | Where | Encoding | Who publishes |
|---|---|---|---|
| **Southbound Sparkplug B** | MQTT `spBv1.0/...` | Sparkplug B protobuf | Field devices (ESP32, simulators). The gateway's `sparkplug` driver is the Sparkplug *host application* and sends `NCMD`/`DCMD` and `STATE` |
| **Internal bus** | MQTT `skyranger/v1/{gateway_id}/...` | JSON (UTF-8) | `skyrangerd` only |
| **Northbound Sparkplug B** (optional, off by default) | MQTT `spBv1.0/...` on a broker the customer chooses | Sparkplug B protobuf | `skyrangerd` acting as a Sparkplug edge node, so Ignition or another host can consume Sky Ranger tags |

Inside `skyrangerd`, components pass the Go structs from tag-model.md and the event envelope below over in-process channels. The internal MQTT bus mirrors those for external observers (Python scripting runtime, integrations, debugging with `mosquitto_sub`). **The history path never depends on MQTT.**

## 1. Sparkplug B: what we rely on

Facts below are from memory of Sparkplug B 3.0 (Eclipse Sparkplug). Items marked UNVERIFIED must be checked against the spec PDF and the Eclipse Tahu `sparkplug_b.proto` before the driver or firmware is finalized.

- Topic: `spBv1.0/{group_id}/{message_type}/{edge_node_id}[/{device_id}]`.
- Message types: `NBIRTH`, `NDEATH`, `NDATA`, `NCMD`, `DBIRTH`, `DDEATH`, `DDATA`, `DCMD`, and `STATE`.
- Payload: protobuf `Payload { timestamp, metrics[], seq, uuid, body }`. `Metric { name, alias, timestamp, datatype, is_historical, is_transient, is_null, metadata, properties, value }`. Use the Tahu `.proto` verbatim, do not hand-write it.
- `seq` is 0..255, incrementing per message from an edge node and wrapping; `NBIRTH` has `seq = 0` (UNVERIFIED: exact rule on whether NDEATH carries seq).
- `bdSeq` metric appears in `NBIRTH` and in the `NDEATH` registered as the MQTT Last Will. It pairs a death with its birth, and it increments per MQTT session, **not** per device reboot. We therefore never use `bdSeq` as a counter epoch.
- `NBIRTH`/`DBIRTH` declare every metric's name, datatype and optional alias. After birth, `NDATA` may use aliases only.
- A host may request a rebirth by sending `NCMD` with boolean metric `Node Control/Rebirth = true`.
- Host application `STATE`: in 3.0, topic `spBv1.0/STATE/{host_id}`, retained, QoS 1, JSON payload `{"online": true|false, "timestamp": <epoch ms>}`. Sparkplug 2.2 used a different topic (`STATE/{host_id}`) and a plain-text payload. UNVERIFIED: exact 3.0 payload field names, and whether edge nodes must wait for STATE before publishing.
- Metric names may contain `/` and tools such as Ignition treat it as a folder separator (UNVERIFIED whether the spec says anything about this).
- Metric datatypes include `Int8..Int64`, `UInt8..UInt64`, `Float`, `Double`, `Boolean`, `String`, `DateTime`, `Text`, `UUID`, `DataSet`, `Bytes`, `File`, `Template`. v1 maps only scalar types; `DataSet`, `Bytes`, `File`, and `Template` metrics are reported in discovery but cannot be approved as tags (`bad_type_mismatch`).

### Sparkplug driver behavior (gateway as host)
- Subscribes to `spBv1.0/{group_id}/#` for each configured `group_ids` entry and publishes its own `STATE` (`host_id` from `Gateway.spec.sparkplug.host_id`) with a retained Will of `online: false`.
- Tracks per edge node: online flag, last `bdSeq`, expected next `seq`, alias table.
- On a `seq` gap, an unknown alias, or `NDATA` before any `NBIRTH`: mark that node's tags `uncertain_last_known` and send `Node Control/Rebirth`. At most one rebirth request per node per `30s`.
- On `NDEATH` with matching `bdSeq` (or a `DDEATH`): all tags of that node/device go `uncertain_last_known`, and the pseudo-metric `@online` goes `false`.
- On broker disconnect: all tags on the connection go `bad_not_connected`.
- Metric `timestamp` becomes `ts_source`; the payload `timestamp` is used if the metric has none.

### Sparkplug address syntax (used in `source.address`)

```
spb://{group_id}/{edge_node_id}[/{device_id}]#{metric_name}
spb://skyranger/esp32-meter01#pulse_count
spb://skyranger/plc-gw/rack2#Motor/Speed           # metric names are case-sensitive, kept as-is
spb://skyranger/esp32-meter01#@online              # pseudo-metric: node (or device) online state
```

The part after `#` is the metric name byte-for-byte. `@online` is reserved and generated by the driver.

## 2. Device profile `skyranger.pulse_meter.v1` (ESP32 firmware contract)

The ESP32 is a Sparkplug B **edge node** with no child devices. `group_id = skyranger` by default; `edge_node_id` is `esp32-` plus the lower 6 hex digits of the MAC address unless provisioned otherwise (must satisfy the segment grammar).

NBIRTH metrics (names and types are normative):

| Metric | Sparkplug type | Semantics |
|---|---|---|
| `bdSeq` | UInt64 | Sparkplug-defined |
| `Node Control/Rebirth` | Boolean | Sparkplug-defined, `false` in birth |
| `profile` | String | Constant `skyranger.pulse_meter.v1`. Discovery uses this to suggest a template |
| `fw_version` | String | Semver, e.g. `0.3.1` |
| `boot_count` | UInt32 | Persisted in NVS, incremented once per boot **before** connecting. This is the counter epoch |
| `pulse_count` | UInt32 | Pulses since boot. Starts at 0 on every boot. Wraps at 2^32. Never reset by any other means |
| `uptime_s` | UInt32 | Seconds since boot |
| `rssi_dbm` | Int32 | Wi-Fi RSSI |
| `heartbeat_interval_s` | UInt32 | Informational, default 60 |

Publishing rules:
- `NDATA` with `pulse_count` when it changes, rate-limited to at most one message per `1s` (the value is cumulative, so coalescing loses nothing).
- A heartbeat `NDATA` every `heartbeat_interval_s` containing `uptime_s`, `pulse_count`, `rssi_dbm`, **even if nothing changed**. This is what lets `liveness` tell "no flow" from "dead device".
- On `Node Control/Rebirth`, re-publish `NBIRTH` with current values (same `boot_count`, current `pulse_count`).
- Timestamps: the device should sync via SNTP to the gateway. If it is not yet synced, it still sends a timestamp (UNVERIFIED whether the spec permits omitting it), and the gateway skew rule (tag-model.md section 5) discards it.
- QoS 0 for NDATA is acceptable because counts are cumulative: a lost message is corrected by the next one.
- Pulse counting must be in an ISR or the PCNT peripheral with debounce; the firmware doc owns the details.

Why the epoch: an MQTT reconnect without reboot (new `bdSeq`, same `boot_count`, `pulse_count` continues) must not be treated as a reset. A reboot (new `boot_count`, `pulse_count` from 0) must be. `counter_total` binds `epoch: raw/boot_count` to tell these apart.

## 3. Internal bus topic namespace

Root: `skyranger/v1/{gateway_id}`. Only `skyrangerd` may publish under it (Mosquitto ACL). Everyone else is a read-only subscriber. All payloads are UTF-8 JSON.

| Topic | Retained | QoS | Payload |
|---|---|---|---|
| `skyranger/v1/{gateway_id}/status` | yes | 1 | `{"online": true, "version": "0.1.0", "started_at": "...", "config_revision": 42}`. Registered as Will with `{"online": false}` |
| `skyranger/v1/{gateway_id}/tags/{tag_path}` | yes | 0 | Canonical value object (README.md). One topic per tag; the path segments become topic levels |
| `skyranger/v1/{gateway_id}/alarms/{tag_path}/{alarm_name}` | yes | 1 | Alarm state object (section 5) |
| `skyranger/v1/{gateway_id}/events/{event_type}` | no | 1 | CloudEvents envelope (section 4). `{event_type}` is the full type string, e.g. `skyranger.config.revision_applied.v1` |

Examples:

```
skyranger/v1/gw01/tags/site1/pumphouse/meter01/flow_rate
skyranger/v1/gw01/tags/_system/connections/local-sparkplug/state
skyranger/v1/gw01/alarms/site1/pumphouse/meter01/leak/leak
skyranger/v1/gw01/events/skyranger.tag.counter_discontinuity.v1
```

Subscribing:
- All values under an area: `skyranger/v1/gw01/tags/site1/pumphouse/#`
- All alarm-related events: `skyranger/v1/gw01/events/+` filtered by type prefix, or a specific type topic.

Rules:
- Values are published after deadband filtering, in `ts` order per tag.
- When a tag is deleted or renamed, `skyrangerd` publishes an empty retained message to its old topic (clears retention) and emits `skyranger.config.revision_applied.v1`.
- No command topics in v1. Writes, acks, and config changes go through the REST API (api.md) so that auth and audit live in one place. The Python scripting runtime will use the REST API for writes.

## 4. Event envelope

Events use **CloudEvents 1.0, JSON structured mode**. Core attribute names (`specversion`, `id`, `source`, `type`, `time`, `subject`, `datacontenttype`, `data`) are as defined by CloudEvents 1.0. Field-level details beyond those core attributes are ours.

```json
{
  "specversion": "1.0",
  "id": "01933b80-1c2d-7e4f-8a9b-0c1d2e3f4a5b",
  "source": "/gateways/gw01/tag-engine",
  "type": "skyranger.tag.counter_discontinuity.v1",
  "time": "2026-11-07T10:22:00.412Z",
  "subject": "site1/pumphouse/meter01/total_volume",
  "datacontenttype": "application/json",
  "data": { }
}
```

- `id`: UUIDv7. Consumers de-duplicate by `id` (QoS 1 can redeliver).
- `source`: `/gateways/{gateway_id}/{component}`, component in `tag-engine`, `alarm-engine`, `config`, `discovery`, `driver-host`, `api`.
- `subject`: tag path where applicable, otherwise the resource id.
- Every event is also written to the `events` table (TimescaleDB hypertable) and retrievable via `GET /api/v1/events`.

Go:

```go
type Event struct {
    SpecVersion     string          `json:"specversion"`      // "1.0"
    ID              string          `json:"id"`
    Source          string          `json:"source"`
    Type            string          `json:"type"`
    Time            time.Time       `json:"time"`
    Subject         string          `json:"subject,omitempty"`
    DataContentType string          `json:"datacontenttype"`  // "application/json"
    Data            json.RawMessage `json:"data"`
}
```

### Event catalog v1 (`data` shapes)

| `type` | `data` |
|---|---|
| `skyranger.tag.counter_discontinuity.v1` | `{"tag_id", "path", "kind": "reset"\|"rollover"\|"implausible"\|"manual_adjust", "prev_raw": "60", "new_raw": "3", "prev_epoch": "7", "new_epoch": "8", "delta_applied": 3.0, "total_after": 1234630.0}` (raw/epoch as strings; uint64) |
| `skyranger.tag.write_completed.v1` | `{"write_id", "tag_id", "path", "value", "requested_by": "user:alice", "result": "ok"\|"error", "error": {"code","message"}?}` |
| `skyranger.alarm.state_changed.v1` | Alarm state object (section 5) plus `"previous_state"` |
| `skyranger.connection.state_changed.v1` | `{"connection": "local-sparkplug", "state": "connected", "previous_state": "connecting", "error": {"code","message"}?}`; states from driver-interface.md section 3 |
| `skyranger.config.revision_applied.v1` | `{"revision": 43, "previous_revision": 42, "applied_by": "user:alice", "comment": "...", "summary": {"tags_added": 9, "tags_changed": 0, "tags_removed": 0}}` |
| `skyranger.discovery.device_announced.v1` | Discovered device object (section 7), first sighting |
| `skyranger.discovery.device_changed.v1` | Discovered device object, when the metric set or profile changes (e.g. new firmware) |
| `skyranger.discovery.status_changed.v1` | `{"discovery_id", "status", "previous_status", "changed_by"}` |

## 5. Alarm state object

```json
{
  "alarm_id": "01933b81-...",
  "tag_id": "01933b7e-...",
  "path": "site1/pumphouse/meter01/leak",
  "name": "leak",
  "severity": "high",
  "state": "active_unacked",
  "shelved_until": null,
  "message": "Flow has not stopped for 2h: possible leak",
  "value": true,
  "quality": "good",
  "active_at": "2026-11-07T12:00:30.000Z",
  "cleared_at": null,
  "acked_at": null,
  "acked_by": null,
  "updated_at": "2026-11-07T12:00:30.000Z"
}
```

`state` is one of `normal`, `active_unacked`, `active_acked`, `cleared_unacked`. Shelving and disabling are orthogonal flags (`shelved_until`, and `enabled` from config) rather than states, so an alarm that clears while shelved still records the correct state. (The alarm design doc may refine this toward ISA-18.2; the state names above are fixed.)

## 6. Raw counts, rollover and reboot: representation summary

- The device publishes `pulse_count` (raw, since boot) and `boot_count` (epoch). It never publishes liters, rates, or totals.
- These land in tags `.../raw/pulse_count` and `.../raw/boot_count` with history, so any total can be recomputed from raw history in an audit.
- `counter_total` (tag-model.md section 7) produces `total_volume`; every non-normal step emits `skyranger.tag.counter_discontinuity.v1` with `kind`:
  - `reset`: epoch changed, or the count went backwards with no epoch bound. `delta_applied` is the new raw value (baseline zero).
  - `rollover`: count passed `modulus`.
  - `implausible`: delta exceeded `max_delta`, so the sample was ignored.
  - `manual_adjust`: operator wrote the total.
- Reports covering a period with a `reset` event flag the period as possibly under-counted, by at most the pulses between the last sample before the reboot and the reboot itself.

## 7. Discovery and config approval flow

```
device NBIRTH ─► sparkplug driver ─► driver host: DiscoveryUpdate (gRPC stream, driver-interface.md)
             ─► discovery service upserts discovered_devices row (status=pending)
             ─► event skyranger.discovery.device_announced.v1 ─► HMI "Discovered" list
operator: POST /api/v1/discovery/devices/{discovery_id}/approve  {template, params, base_path, instance_name}
             ─► server builds a TagGroup patch ─► validated as a config draft ─► diff shown
operator: POST /api/v1/config/drafts/{draft_id}/apply
             ─► revision N+1 ─► event skyranger.config.revision_applied.v1
             ─► tag engine creates tags ─► driver Subscribe ─► values flow
             ─► discovered device status=approved, linked to instance
```

Rules:
- Discovery never creates tags. Only an applied revision does (decision 4).
- `approve` with `"apply": true` combines draft and apply into one step for the common case; the diff is still recorded in the revision.
- Status values: `pending`, `approved`, `ignored`. `ignored` hides the device and suppresses re-announce events until its metric set or profile changes.
- Discovery for drivers that cannot announce (Modbus TCP) is operator-initiated: `POST /api/v1/connections/{name}/browse` calls the driver's `Browse`, and the results populate the same discovered-device list.
- If an approved device later announces a changed metric set, status stays `approved` and a `device_changed` event fires; existing tags are untouched. New metrics are shown as "unmapped" in the HMI.
- An unapproved device's data is dropped after updating `last_seen`. No history is kept for unapproved devices.

### Discovered device object

```json
{
  "discovery_id": "01933b7f-...",
  "connection": "local-sparkplug",
  "device_key": "spb://skyranger/esp32-meter01",
  "status": "pending",
  "profile": "skyranger.pulse_meter.v1",
  "suggested_template": "pulse_water_meter",
  "first_seen": "2026-11-07T09:58:01.000Z",
  "last_seen": "2026-11-07T10:00:00.000Z",
  "online": true,
  "attributes": { "fw_version": "0.3.1" },
  "points": [
    { "address": "spb://skyranger/esp32-meter01#pulse_count", "name": "pulse_count", "native_type": "UInt32", "datatype": "uint64", "writable": false },
    { "address": "spb://skyranger/esp32-meter01#boot_count",  "name": "boot_count",  "native_type": "UInt32", "datatype": "uint64", "writable": false }
  ],
  "linked_instance": null
}
```

`device_key` is the driver's stable identity for the device (an address prefix). `(connection, device_key)` is unique. `suggested_template` comes from matching `profile` against a template's `metadata.annotations["skyranger.io/profile"]`, if any.

## 8. Northbound Sparkplug (optional)

When enabled (`Gateway.spec.sparkplug.northbound`, schema owned by the integration doc), `skyrangerd` publishes as edge node `{gateway_id}` in a configured `group_id`. Metric name = tag path; Sparkplug datatypes map from our six types (`bool`→Boolean, `int64`→Int64, `uint64`→UInt64, `float64`→Double, `string`→String, `datetime`→DateTime). Quality is carried as a metric property (UNVERIFIED: the property name Ignition expects for quality). Not needed for milestone 1.

## Decisions made
1. Three MQTT families with separate roots: southbound `spBv1.0`, internal `skyranger/v1/{gateway_id}`, optional northbound `spBv1.0`. Only `skyrangerd` publishes on the internal root.
2. Internal bus is JSON: retained per-tag value topics (path = topic levels) plus CloudEvents 1.0 events at `events/{type}`. No command topics; writes go through REST.
3. The ESP32 publishes `pulse_count` since boot plus an NVS-persisted `boot_count` epoch and a 60 s heartbeat. `bdSeq` is never used as a reboot indicator.
4. Every counter anomaly is an explicit, stored `counter_discontinuity` event.
5. Discovery produces a pending record, and approval produces a config draft. Tags exist only after a revision is applied.
6. The Sparkplug driver requests rebirth on gaps, rate-limited to one request per node per 30 s.

## Alternatives rejected and why
- **Custom JSON-over-MQTT protocol for devices**: Sparkplug B is already decided, gives birth/death state for free, and is what other SCADA hosts speak.
- **Protobuf on the internal bus**: harder to debug with `mosquitto_sub` and to consume from Python; message rates at milestone scale are tiny.
- **Using `bdSeq` or the Sparkplug `seq` as reboot detector**: they change on reconnect without reboot, which would trigger false resets.
- **Device sends liters or a persisted lifetime total**: puts business logic and flash wear on the device; gateway computation is auditable from raw history.
- **History via MQTT subscription**: broker outage or QoS 0 loss would create history gaps; history is written in-process.
- **Command topics for writes**: two auth/audit paths. Deferred until scripting needs it.
- **Auto-approve devices that match a profile**: violates decision 4, and a device could silently create tags.
