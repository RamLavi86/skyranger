## 2. Security levels

IEC 62443 describes four security levels, SL 1 to SL 4, as protection against increasingly capable attackers (from casual or coincidental violation up to sophisticated means with extended resources); SL-T (target), SL-C (capability) and SL-A (achieved) are distinguished. Exact wording and the vector of seven values per level are UNVERIFIED.

Our positioning:
- **Target capability: SL 2 for `skyrangerd` and the reference system**, consistent with the zone table in 05 section 5 and with the threat model scope (T1 to T7, not T8; 01).
- SL 3 or SL 4 is not a goal. A customer needing it needs defence in depth and an independent assessment far beyond this product.
- We state capabilities, not levels achieved, until an assessor says so (section 5).

## 3. Foundational requirements mapping (self-assessment starting point)

The seven foundational requirements (FR) are: FR 1 Identification and authentication control, FR 2 Use control, FR 3 System integrity, FR 4 Data confidentiality, FR 5 Restricted data flow, FR 6 Timely response to events, FR 7 Resource availability. Controls below are designed in this folder; "Gap" is what a SL 2 assessment will probably still ask for. Individual requirement IDs are deliberately not listed (UNVERIFIED).

| FR | What we do (file) | Gap or planned |
|---|---|---|
| FR 1 Identification and authentication | Unique local users, argon2id, no default credentials, one-time setup code, API keys per service account, session limits (02); per-device MQTT identity (04); site PKI, mTLS for sync (03); TOTP for admin and remote (v1.1) | MFA is not in v1; account lockout deliberately replaced by throttling for availability (02), so the rationale must be documented for assessors; password policy configurability; OIDC/LDAP later |
| FR 2 Use control | Four roles mapped to permissions, deny by default, per-route test (02); confirmation and write audit (05-hmi-api/05); remote access disabled by default (05) | Per-area scoping (open question in 02); two-person approval not offered |
| FR 3 System integrity | Signed images, digest pinning, signed bundles, rollback, SBOM (07); ESP32 secure boot and flash encryption (04); input validation and fuzzing of device-facing parsers (07); audit hash chain (08); hardening (09) | Boot-chain integrity on the host depends on hardware (TPM, Secure Boot) per deployment doc; reproducible builds not complete |
| FR 4 Data confidentiality | TLS 1.2+ on all TCP links under our control (03); secrets encrypted at rest with envelope encryption (06); encrypted backups (10); LUKS (09) | Modbus TCP and other cleartext southbound protocols are residual risk by design (01 section 7); history data at rest relies on disk encryption |
| FR 5 Restricted data flow | Purdue zones and conduits, default-deny firewall rules, host nftables, outbound-only cloud and remote access (05); per-driver UIDs (09) | Per-driver network restriction not achieved in v1 (09 open question); data diode not offered |
| FR 6 Timely response to events | Audit log with fixed schema and off-box syslog forwarding (08); `_system/security/*` alarms (08 section 5); vulnerability handling process (13) | No SIEM integration beyond syslog; incident response playbook is a deliverable (section 6 here) |
| FR 7 Resource availability | Rate limits and connection caps (02, api.md); bounded queues and backpressure (contracts); A/B update and rollback (07); backups and restore drills (10); watchdog and power-loss design (deployment) | Denial of service on the field Wi-Fi is not defendable (01); redundancy/HA not offered in v1 |

Also needed for a real assessment but not mapped one-to-one above: documentation of security-related configuration ("hardening guide", 09 plus a customer-facing edition), a defence-in-depth guide, a security guideline for integration, and a secure-by-design record.

## 4. Process alignment with 62443-4-1 (do now)

62443-4-1 organises the secure development lifecycle into practice areas (recalled as: security management, specification of security requirements, secure by design, secure implementation, security verification and validation testing, management of security-related issues, security update management, security guidelines; the exact list, count and numbering are UNVERIFIED). Our lightweight equivalents:

| Practice area (UNVERIFIED names) | Our evidence |
|---|---|

| Specification of security requirements | Threat model (01) and the normative principles in the README; this mapping |
| Secure by design | Architecture decisions (single door for change, segmentation, signed-or-no-run); STRIDE per boundary; re-run on each new boundary (01) |
| Secure implementation | Coding rules (parameterized SQL, no custom crypto, strict parsing), code review, static analysis (07 section 5) |

| Management of security-related issues | Disclosure policy, triage SLAs, advisories (13) |
| Security update management | Signed releases, rollback, support policy with end-of-life dates (07, 13) |
| Security guidelines | Hardening guide, handover document, safety statement (09, 11) |

Records to keep from day one, because they are cheap now and expensive to reconstruct: threat model revisions, review sign-offs per release (a signed checklist from 14), vulnerability tracker entries with timelines, SBOM per release, test reports, supplier component reviews.

## 5. Realistic certification path

Certification is expensive and slow relative to a one-person integrator-first business (decision 5). The path is staged, and each stage stops being worth it if no customer pays for it.

| Stage | When | What | Cost shape (indicative, UNVERIFIED) |
|---|---|---|---|
| 0 | Now | Build the evidence trail: section 4 records, this mapping, documented SL 2 target | Time only |
| 1 | Before first paid deployment | External review of threat model and a penetration test of a staged deployment (01 and 14 open questions) | Low five figures at most for a small scope |
| 2 | After 2 to 3 projects | Formal **gap assessment** against 62443-4-1 and 62443-4-2 (software application) by an accredited certification body, to learn the real gap list | Moderate |
| 3 | Only if a customer or tender requires it | Certification of the **development process** (4-1) first; a process certificate is the natural first step because it covers every release | Significant; recurring surveillance audits |
| 4 | After stage 3, if worth it | Component certification against 4-2 for `skyrangerd` (software application) at SL 2 | Significant; re-certification on major changes |
| Never (for now) | | System (3-3) certification of a deployment: that belongs to the integrator and customer for a specific installation | |

Certification schemes known from general knowledge: ISASecure (Security Development Lifecycle Assurance and Component Security Assurance programs) and certification bodies such as TUV entities, DEKRA and others offer 62443 schemes. Which bodies are accredited for which parts, and current program names and scope, are UNVERIFIED; check before approaching anyone.

Rules until a certificate exists:
- We say "designed to align with IEC 62443-4-1 and targeting 62443-4-2 SL 2" and we link the evidence. We never say "compliant" or "certified".
- Customer tender responses use a table of controls (section 3) with honest gaps listed, not a checkmark column.
- The integrator business may later pursue 62443-2-4 as service provider (UNVERIFIED applicability); it is separate from the product.

## 6. Incident response (minimum, for FR 6)

A one-page playbook delivered with each project: who to call, how to isolate (disable remote access, unplug field VLAN, stop `skyrangerd` without stopping the process), how to preserve evidence (export audit and checkpoints, copy the latest backup, do not reboot a suspected-compromised box if volatile evidence matters), when to restore (10 section 5), and who notifies the customer's authority if required. Contact paths follow the disclosure policy (13). Notification duties under regulation (water sector, EU NIS2, CRA) are UNVERIFIED and customer-specific; the integrator confirms per customer.

## 7. Regulatory neighbours (awareness only)

- **EU Cyber Resilience Act**: requirements for products with digital elements, including vulnerability handling and SBOMs. Applicability, dates and obligations for an open-source component or integrator-delivered system are UNVERIFIED and need legal review before selling in the EU (also noted in 07).
- **NIS2 / sector rules for water utilities**: the customer's obligation; our deliverables (audit, SBOM, disclosure process) help but do not discharge it. UNVERIFIED per jurisdiction.
- **NIST SP 800-82 (ICS security guide)** and CISA ICS guidance: useful as reading lists and customer vocabulary; not requirements on us. Current revision numbers UNVERIFIED.

## Decisions made
1. Align the development process with 62443-4-1 now; self-assess `skyrangerd` against 62443-4-2 at SL 2; target SL 2 only.
2. Do not claim compliance or certification; publish a control table with honest gaps.
3. Certify the process before any component, and only when a paying customer requires it.
4. Keep an evidence trail from day one (threat models, signed checklists, SBOMs, test and vulnerability records).
5. Every clause number, requirement ID and scheme detail is marked UNVERIFIED until checked against the standard.

## Alternatives rejected and why
- **Aiming for SL 3 or SL 4**: needs capabilities (strong isolation, hardware roots of trust, formal processes) disproportionate to the market and team.
- **Certification first, product second**: certification covers a product that exists and a process that is repeatable; premature and expensive.
- **Mapping every individual requirement ID now**: invites errors from memory; the FR-level map is what we can stand behind today.
- **Ignoring 62443 until a customer asks**: the evidence trail is nearly free early and nearly impossible to fabricate later.
- **Claiming "62443-ready" or "compliant" in marketing**: unverifiable and a liability.
